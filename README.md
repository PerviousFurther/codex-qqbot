# llm-watch-video

A QQ chat and video assistant using Codex with restricted MCP tools. It can browse Bilibili, read public webpages, inspect received pictures, and retain images for later appropriate replies. One global persona, a small role-state snapshot and optional shared Markdown notes give conversations continuity; chat histories, attachments, and permissions remain scoped.

Ordinary replies use short natural phrases. Video shares contain a title, full link, and one or two comment sentences. Continuous browsing, discussion collection, video pushes, natural participation, and idle starters require explicit administrator configuration.

See [HANDOFF.md](HANDOFF.md) for deployment locations/status, [AGENTS.md](AGENTS.md) for development constraints, and [docs/architecture.md](docs/architecture.md) for module ownership. Documentation is maintained in English.

## Commands and access

| Command | Purpose | Access |
| --- | --- | --- |
| `/help`, `/status` | Help and conversation status | Conversation users |
| `/history [page]`, `/video BV...` | Public video history and selection | Conversation users |
| `/settings`, `/manage` | Administrator home | Bot administrator, private chat |
| `/groups [page]` | Group permissions, scheduling, model, and reply settings | Bot administrator, private chat |
| `/preferences` | Topics, exclusions, duration, selection style | Bot administrator, private chat |
| `/persona` | Global persona presets/custom description | Bot administrator, private chat |
| `/models [page]`, `/model model-name` | Model selection | Bot administrator, private chat |
| `/thinking`, `/reply` | Current private chat's reasoning effort and reply style | Bot administrator, private chat |
| `/stop [group-id\|all]`, `/pause` | Stop tasks and invalidate unsent work; `/stop` offers target selection | Bot administrator, private chat |
| `/memory`, `/group-memory group-id` | Context refresh/compaction and confirmed record clearing | Bot administrator, private chat |
| `/compact`, `/reset` | Compact or refresh current private model context | Bot administrator, private chat |
| `/bilibili-login [check]` | Bilibili QR login/account check | Bot administrator, private chat |
| `/debug` | One combined diagnostic TXT report | Bot administrator, private chat |

Slash commands, including unknown/malformed commands, finish locally before inference. Read-only pages do not wait for model tasks. Session/model changes serialize explicitly; stop commands act immediately.

Official event OpenIDs determine identity. QQ group administrators/owners are not automatically bot administrators. Configure `WATCH_ADMIN_OPENIDS`, or let the first valid private sender claim the role when no administrator is configured/saved; `WATCH_CLAIM_FIRST_ADMIN=false` disables new claims. A private OpenID and a group member OpenID are not interchangeable. Group speakers have no bot-administrator identity binding or administrator markers. Administrator identity and management commands are private-chat only.

### Operator settings

The administrator home has six sections: Private chat, Groups, Persona, Video preferences, Video browsing, and Data. Stop tasks and Run feedback are available directly from home. Private chat groups model/reasoning preferences and the public-private-chat switch; Data links to scoped conversation maintenance and global video retention. Group pages expose daily switches, model, and a small More page for timing, reasoning, notes, unified Run feedback and reply-limit reminders. Each group has one opt-in Run feedback switch for processing states and actual operation starts, completion/failure/interruption and elapsed time. All feedback is sent privately to bot administrators in plain operator-facing language, without tool/protocol identifiers, arguments, result bodies or reasoning. Feedback never posts to the source group, resumes stopped tasks or releases another sender's reservation. Pages explain effects and deletion scope without protocol, tool or storage details. Custom persona usage is still measured against its existing token budget, without exposing the tokenizer in the interface.

`/settings chat` and `/settings data` open the two subpages. All administrator commands remain private-only; reading settings does not enable features or resume paused groups. Conversation/video clearing still requires the existing single-use confirmation. Models keep return/previous/next buttons within the five-button, single-column limit. The QQ private menu uses video/history/help, a settings submenu and task stopping. On its normal startup synchronization, the service replaces only its own current/known older menu entries, preserving unrelated entries and the original backup. No live menu update is implied by source changes.

### Persona and preferences

`/persona custom <description>` sets the global persona; `/persona reset` restores the natural assistant. Custom descriptions have a 500-token limit counted offline with pinned o200k_base. Overflow preserves the existing value; previews are bounded, while the model receives the full description. Persona changes apply next turn, resume the original thread, and leave existing video comments intact. Facts/summaries/diagnostics remain objective.

Preferences are scoped to the configuring administrator. Examples:

```text
/preferences topics science, history, indie games
/preferences avoid horror, spoilers
/preferences duration short
/preferences style relaxed and entertaining
```

Duration values are `any`, `short` (up to ten minutes), `medium` (10–30 minutes), and `long` (over 30 minutes). `/preferences topics 清空` and `/preferences avoid 清空` clear individual fields; `/preferences reset` restores defaults. The current explicit request takes precedence.

Model replies preserve the exact text, punctuation, line breaks and message boundaries selected by the model, subject to credential redaction and platform transport support. All chat output uses `send_reply`; turn completion sends no additional text. Ordinary prose stays one immediate message per call; local media references create ordered text/media/text boundaries. There are no reply-style settings, local character targets, automatic prose splitting, source banners, total ordinary-message count caps or local send cooldowns. Actual QQ rejection is still reported; the service does not retry uncertain delivery. Models and reasoning effort remain scoped and validated against the current model catalogue.

## Groups, memory, and shared state

Authorize a group through private `/groups`. Collection and proactive features default off and require reply authorization; natural participation/idle starters also require collection. A local switch cannot grant QQ all-message access. Only actually delivered messages are collected, before mention filtering; explicit mentions trigger the same collected-message batch immediately instead of entering the foreground queue. Mentions use the same collection, natural-participation and stop settings as other group discussion. Control commands do not enter discussion memory or automatic-chat triggers.

A discussion batch is eligible when any condition is met: 20 pending messages, 1,000 pending characters, or 180 seconds since the latest collected member message. Each new collected message resets that waiting deadline. There is no minimum interval between model batches; ordered sends, foreground priority and error backoff still apply. Existing per-group count/character/wait values remain in use, with wait measured from the latest message. Group More → Conversation timing configures these thresholds and the history window. Natural participation can answer, react, ask questions, or remain silent. Idle starters make at most one attempt per quiet period, defaulting to one hour after enablement/latest member message; a new member message starts another period. Foreground work takes priority.

“Pending” means **not yet supplied to model input**, not “not yet answered.” Foreground bodies are recorded after the model accepts the turn; event-tool bodies are recorded on intake. Mentions and ordinary group messages share one pending batch and exact message IDs in SQLite. A pending bot mention makes that batch immediately eligible; accepted input removes its immediate trigger along with the supplied messages. The separate completed-batch cursor is bookkeeping only and never controls input replay. Receipts follow original-record retention; previously completed batches and foreground seen IDs initialize them on upgrade. Explicit history reads do not change automatic-input receipts.

### Messages during a model turn

Each conversation has one in-memory event inbox. New private messages are immediately eligible. Group messages share one batch: a bot mention, or the configured count/character/latest-message condition, makes pending messages eligible, counting only messages not yet supplied to the model. Group-event interruption requires natural participation enabled; collection alone does not enable it. New messages do not cancel work in unrelated conversations. Foreground priority still prevents starting new background tasks while foreground requests are pending.

The service first sends a `turn/steer` event notice to the active model. `check_pending_events(turn_id)` returns one ready event with scoped new message bodies, plus guard changes and prior-interruption notices through the existing private turn IPC. Eligible reply turns can answer the new messages and continue their original work. Successful intake immediately records the body as supplied and skips its queued inference. Completion, silence, failure and cancellation never automatically replay a supplied body. Turns without an appropriate chat sender, including idle starters whose quiet-period permission is no longer valid, leave new requests queued for the next turn.

`wait_reply(turn_id, timeout_seconds=30)` lets an eligible model wait before ending its turn and directly receive the next message event. Each call waits at most 50 seconds to fit the existing IPC deadlines; `timedOut=true` is a normal empty result. Existing pending input returns immediately. While explicitly waiting, any collected group message can enter the inbox without reaching count/character/wait thresholds; collection, natural-participation, stop, reservation and retry-backoff gates still apply. Outside an explicit wait, normal batching is unchanged. Media notices do not end the wait. Stop, cancellation, turn closure and IPC disconnect release the waiter. Input receipts and scoped authorization use the same intake path as `check_pending_events`; the tool does not send a reply. There is no default whole-turn deadline; stop, cancellation, per-request and per-tool deadlines remain active. Waiting is optional, not a mandatory step or an idle polling loop.

`set_interrupt_guard(turn_id, enabled)` has no duration. The model chooses when to enable/release it; completion, failure and cancellation clear it automatically. It prevents ordinary unread messages from cancelling the turn while messages still accumulate and trigger notices. The model can read/reply to messages and receive media notifications with the guard enabled. Administrator stop, authorization revocation and delivery failure retain their immediate cancellation/stop paths.

`read_media(turn_id, attachment_id|image_id|media_id, selection)` reads received QQ video and GIF through the same asynchronous decoder. Omit the selection to request metadata; select frames with `timestamps`, or `start/end/interval` in seconds (end exclusive). It immediately returns `pending`, `ready` or `error`, with any frames already cached. Equivalent selections reuse one background task and repeated reads replay its growing cache. `media_progress`, `media_ready` and `media_error` notices steer only the current turn; call `check_pending_events` and read the original selection again. A notice can race with reads/closure: returned state is authoritative. Models can intake/reply to messages while decoding.

GIF disposal/transparency is composited by the same ffmpeg pipeline as video. Each query uses one continuous native decode and yields complete PNGs with actual presentation timestamps, rather than spawning a process per requested timestamp. No fixed three-frame sampling; omitted selections do not invent sample points. Output is selected visual evidence, with no claim to have watched unsampled actions. Speech requires a separate explicit audio query. Bilibili media-stream/audio integration is **ON HOLD** until the QQ pipeline is validated and extension is explicitly requested.

For speech in a received QQ video, `read_media({turn_id, media_id, track: "audio", start, end})` starts an optional local-ASR side branch over the same authorized file. `track` defaults to `video`; ordinary visual/metadata queries never start ASR. Audio requires an explicit range of at most 120 seconds and accepts no frame timestamps/interval. Its separate serial queue allows frame reads to continue while recognition runs; local audio attachments and video speech share the existing global single-job slot. Busy/no-audio/unconfigured/range errors are explicit and cached without automatic retry or source fallback.

Audio reuses PCM → VAD → transcript streams. `segments` are available while pending and use the original video's timeline; completion with no recognized segments returns `NO_SPEECH_DETECTED`. Each range has up to 0.25 seconds of boundary context per side, 100 segments/12,000 characters and a 100-second deadline. Segment timestamps retain real VAD boundaries; `contextOverlap` flags segments extending outside the requested range. Exact duplicate segments within a query are removed; adjacent queries can repeat boundary context, so consumers must not interpret that as repeated speech. Transcription does not establish music/sound-effect/emotion/speaker understanding. No transcripts enter shared memory or diagnostics automatically.

Media bounds: video 64 MiB/900 seconds, GIF 16 MiB/120 seconds, dimensions up to 8192 per side/16,777,216 pixels, PNG output fitting 1280x720, 45 seconds per decode/probe, 64 selected samples per query, 32 queries per open media, four open media and 32 MiB total frame/transcript cache per turn. Capacity exhaustion fails explicitly; reduce the requested range/rate or close media. Reads preserve scope, retained-existence and collection-access checks, including cached results. `close_media(turn_id, media_id)` cancels jobs and releases both branches, decoder/files/cache. Turn completion/failure/cancellation closes **all** media sessions and the lifecycle subscription before reuse; there is no cross-turn continuation, automatic new turn, seek tool or additional sleep tool. Internal streams do not incrementally update a single MCP response: frames reach the model via successive cache reads.

Without a guard, pending events get a ten-second grace period for model intake. Further arrivals do not extend that deadline. If messages remain unread, the service cancels the old turn, invalidates its sender and lets queued work run. The next turn receives task status/message IDs and up to 32 recent accepted replies per interrupted turn (up to four handoffs), without copying the original incoming bodies, with explicit instructions against replay. Cancellation starts a successor turn; it is not coroutine pause/resume. Input receipts are persistent; the event inbox, guards and handoffs are process-local and do not promise recovery of queued work after a crash. This uses the documented [Codex App Server steering protocol](https://learn.chatgpt.com/docs/app-server); live compatibility and QQ display require deployment validation.

Group SQLite records retain seven days/5,000 originals, with 500 characters per original. Automatic discussion batches include up to 40 not-yet-supplied messages inside the configured input window, default ten minutes (1–1,440 minutes per group), within the existing size budget. Foreground requests include only their own new message; foreground/discovery/idle turns do not attach recent message snapshots. New turns, thread expiry and explicit refresh do not reattach recent history. Models can explicitly retrieve retained originals when needed. Timestamps use `YY/MM/DD-HH:mm` with an explicit `Asia/Shanghai` timezone (Beijing time, UTC+08:00). Cumulative summaries stay behind explicit retrieval because they can contain older material. Group model threads are detached when their oldest automatically supplied context expires or the window changes; model/effort preferences, deduplication IDs and retained records remain intact. Existing unbounded group threads are detached on their next turn; private threads keep their existing lifecycle. `recall_group_context` retrieves current-group records by member/time/keyword/revision cursor, defaulting to the configured window when `since` is omitted. Explicit ISO-8601 time ranges can retrieve older retained originals; compaction still reads a complete unfiltered prefix and its previous summary; `compact_group_context` saves a cumulative summary of at most 1,500 characters using a complete-prefix read token. Summaries are not exact quotations. Compaction retains originals and schedules model-context compaction after the turn. Permission, epoch, coverage, and summary version checks protect concurrent collection.

Incoming QQ text preserves face codes and platform-supplied face names, including face-only messages. Message formats distinguish ordinary text (`0`), cards (`3`), parallel content (`101`), forwarded records (`102`), quotes (`103`), and unknown types. Cards expose bounded titles/descriptions and non-credential HTTP(S) links from delivered structured fields, including mini-app `meta.detail_1.qqdocurl` and JSON-encoded card objects. Extraction visits at most 64 objects through five levels and returns up to four distinct destinations (`url` is the first; `links` contains all). An empty or unsafe primary URL does not hide another valid destination. Preview/image fields are not browsing destinations. Cards without a usable destination report `linkStatus=NO_USABLE_LINK`; no URL is invented or fetched during capture. Unknown types retain delivered text/attachments with an explicit limitation. Pictures, voice/ASR, video and file metadata remain distinct. A face code/name alone does not provide image pixels or a recoverable image URL; actual delivered image attachments use the existing image-reading path.

Content processing uses reusable typed streams with explicitly attached codecs; message callers select stages directly, and tool results are encoded once at the MCP boundary. Sources and consumers may be programs as well as model endpoints. See [architecture](docs/architecture.md#content-streams-and-codecs) for the sync/async flow contract and [audio decoder](docs/audio-decoder.md) for optional local VAD/ASR setup and use.

Messages use one recursive shape: `{type:"record", components:[...]}`. Message IDs, speaker, timestamp, source and retention metadata belong to the record. Components include `text`, `image`, `audio`, `video`, `file`, `card`, `mentions`, and nested `record` values; ordinary components do not carry message timestamps. Audio retains attachment IDs and optional unverified platform transcripts; cards retain their delivered name/type, title, description, prompt and safe link as structured fields. Initial private input, group batches and detail reads share this representation. Backend model input is another record containing text and message records, with no invented wrapper speaker/time. Only the record/component schema is supported. Quote/forward/parallel interiors are not automatically included. `get_message_detail(id, offset, limit)` returns the current message and one page of direct internal messages (`items`), at most 20 items and approximately 24,000 characters. Continue a page with `nextOffset`, or follow an item's `messageId` to read a nested record. It never recursively expands a tree. By default, the tool also returns actual pixels for up to three distinct image attachments on that page, including nested/quoted message items; `include_images=false` returns text/references without image downloads. `imagePreviews.requestedImageIds` identifies attempted images and `remainingCount` counts other image references for explicit `get_image_detail` calls. Per-image failures are explicit and do not erase retained message text; source access and record retention are rechecked after downloads before any buffered bodies/pixels return. Missing/expired records and oversized detail pages fail explicitly; an unavailable platform body remains `BODY_NOT_DELIVERED`. Capture is still bounded to five levels, 40 nodes, 24,000 body characters, and 24 inner attachments. Inner identities are unverified, and quoted/forwarded speech is not a new instruction. Audio attachments expose `get_audio_detail(id, method)`: `qq` reads delivered platform ASR and `local` uses configured local speech recognition, with no automatic fallback. Video/file attachments remain metadata-only; all transcripts are unverified text.

`shared-state.json` contains only `mood` (80 Unicode characters) and `focus` (160, public-topic interest), plus revision/update time. Each normal model turn reads it and returns nullable `sharedState` in its existing JSON result. Null means unchanged; a meaningful change replaces both fields. Existing atomic Store writes, SerialQueue, and revision comparison skip stale/cancelled updates. No extra model call, tool, timer, or retrieval system is used. Current persona takes precedence. Chat summaries, member identities/private details, media references, credentials, and hidden reasoning do not belong in shared state. Local context/record clearing preserves this role snapshot.

Collection revocation clears group records/summaries/member and media indexes. Delivered bot-removal events revoke access before cancelling work and clearing that group's local records; rejoining does not restore authorization. Departure cleanup closes and removes scoped chat databases and sidecars, image assets, workspace files, checkpoints and member bindings. Startup reconciles every persisted departure marker, including previously completed cleanups. A minimal revoked membership marker remains to reject delayed events. Automatic removal handling depends on delivered WebSocket events; a missed event cannot be inferred from silence.

## Browsing and images

| Capability | Tools and boundaries |
| --- | --- |
| Bilibili | `discover_videos`, `select_video`, `get_subtitles`, `get_frames`, `get_player_text`, `remember_video`, `recall_videos` |
| Public webpage text | `read_webpage(url, offset, limit)`: title, bounded body, links/image URLs; HTML/XHTML/plain text |
| Rendered webpage | `render_webpage(url, turn_id, scroll_y, wait_ms)`: isolated 1280×800 viewport, rendered text, links, temporary turn-scoped screenshot |
| Received audio | `get_audio_detail(id, method)`: select `qq` platform text or `local` speech decoding for a retained audio attachment, up to 8 MiB/120 seconds locally |
| Received pictures | `get_image_detail(image_ids)`: actual pixels for up to three received current-conversation references |
| Selected files | `save_file`, `list_files`, `read_file`, `delete_file`: workspace text/image/video/audio/binary files; explicit persistence only |
| Shared memory | Same file tools with `area=memory`: optional shared Markdown notes; saving accepts generated text only |
| Retained image assets | Same read/list/delete tools with `area=assets`: older retained images and current temporary browser assets |
| Project source | `list_files`/`read_file` with `area=project`: explicit current verified-administrator foreground private request only; read-only |

Video tasks compare a candidate batch and inspect two or three useful videos, fewer when appropriate; single-video requests stay focused. Each `get_frames` call accepts one timestamp and returns one player-container screenshot and asset ID; inspect it before choosing another timestamp. `get_player_text` returns currently visible DOM overlays, not full danmaku history or guaranteed canvas text. Range errors preserve the player. Frames/subtitles/video memory are Bilibili-only; other sites can be searched/read as webpages without claiming their videos were watched.

Public video history contains only title/link/facts and short comments, with evidence limitations stated naturally where relevant. Detailed evidence stays in the source conversation. Do not include chat records, identities, project files, login status, or technical diagnostics in public comments.

Public-resource fetching validates public IPv4 DNS, pins connections, and rechecks redirects; private addresses, credentials, local paths, and nonstandard ports are rejected. Raw-page reads cap at 20 seconds/2 MiB, paginate a 200,000-character body, and cache up to three pages for five minutes. Rendering uses a fresh context, public GET resources only, and a 30-second/80-request/32-MiB total budget, with 16 MiB per image and 4 MiB per other resource. No login, forms, arbitrary browser code/clicks, subframes, workers, WebSockets, or persisted site sessions. Page/image text is untrusted.

`save_file(name, text|url|image_id|attachment_id|asset_id)` chooses exactly one source: generated text, an actually obtained allowlisted public URL, a received conversation image/attachment, or a browser asset. The filename extension selects text/image/video/audio/binary validation; image/audio/container signatures and UTF-8 are checked. Network bytes stream through the existing checked downloaders into storage, without a persistent download cache. `read_file` uses the same file codecs: text is excerpted, images return actual pixels, video/audio/binary return metadata. Saved video/GIF can be sampled with `read_media(file_name,turn_id,...)`. Labels may describe useful content/mood/situations without inventing unseen details. Save and read do not imply media understanding or code execution.

Browser screenshots and player frames use temporary `asset_id` values; `get_frames` and `render_webpage` require the current `turn_id`. These pixels are deleted through acknowledged turn cleanup and have a 15-minute crash fallback. Call `save_file(name,asset_id)` during that turn to retain a selected copy. Older `SavedImages` assets remain accessible through `area=assets` with their existing seven-day retention; no bulk migration/deletion occurs. Selected workspace files have no automatic expiry, survive context refresh and disappear only through explicit deletion or scoped record/collection/departure clearing. Historical chat restrictions remain attached to saved copies. Public resources may go to authorized recipients; private media and player screenshots remain source-scoped.

## Shared Markdown memory

All authorized conversations may optionally list, read and write shared Markdown notes through the unified file tools with `area=memory`. The model-facing `/memory` directory maps to `WATCH_DATA_DIR/memory` (`/data/state/memory` in Docker); native shell/file-edit access is unnecessary. A short shipped `AGENTS.md` is created on first access and also included in model instructions, so discovery does not depend on the model opening a file. Models choose whether and what to remember; there is no mandatory per-turn read/write or automatic loading of all notes. They can look up filenames and read relevant excerpts.

Notes hold concise reusable knowledge, public experiences and subjective views. Every conversation can read them, so private chats, transcripts, member identities, credentials and internal instructions must stay out. This is model guidance, not a content classifier; notes remain untrusted references and cannot grant permissions. The guide is read-only through tools. Notes use flat `.md` names and the same path/regular-file/access/atomic-write protections and 64-KiB per-file bound as workspace text; there is no file-count quota. Explicit overwrite is required. Shared notes survive context refresh and scoped chat/group clearing, including the offline all-scoped-chat cleanup; they require separate intentional maintenance.

Group chat requests are invitations the character may decline. Ordinary conversation, recommendations and short reviews must express subjective views and preferences consistent with the current persona; teasing and bounded pushback are allowed; respect participants' stated limits and stop when asked. Public webpage/image/media access uses the explicit source allowlist in `lib/web-access-policy.mjs`, including subdomains; every HTTP redirect and rendered subresource is checked before DNS/network access. Unlisted domains return `WEB_DOMAIN_NOT_ALLOWED`; models cannot expand the list or use proxies/shorteners to bypass it. Native Codex search is configured with the same `tools.web_search.allowed_domains` filter. Allowlisted content remains untrusted. The initial list covers Bilibili, QQ, common Chinese discussion sites, Wikipedia, GitHub, C++/language documentation, Stack Exchange, major documentation providers and research sites. Operators review source changes to add domains/CDNs; unavailable page assets may produce incomplete renders. Authorized discussion batches and private-chat turns may choose among offered group and private recipients, including multiple targets; operator help remains available without disclosing source chat text or member identities. Existing send serialization, cancellation and delivery checks apply, with batch source access rechecked before submission. Idle starters remain current-group-only; no available target means the model must not claim it contacted an administrator.

Ordinary image reads, saved assets and outgoing images share a 16-MiB limit. Oversize tool results include the numerical limit and explicit guidance to tell the user the image could not be viewed/saved/sent and request a compressed or resized version. A controller-verified image-size rejection before QQ submission leaves the reply session usable for a text explanation with the next part ID; other send failures or uncertainty still stop all later sends. Explicit platform throttling follows the separate rejected-part behavior described below. Image retention has no count or aggregate-byte quota. Rendering permits 16 MiB per image resource/screenshot, 4 MiB per other resource and 32 MiB total.

Rendering resolves and validates document redirects in the backend before navigating Chromium to the final URL, preserving document-relative URLs. Resource redirects are also resolved by the checked downloader and served as final bytes, never as a browser redirect through the deny proxy. Relative URLs inside a stylesheet served from a different final directory may remain incomplete.

Public downloads accept identity, gzip, zlib deflate and Brotli response bodies, even when a server ignores the identity request preference. Decoding is streamed; both transferred and decoded sizes are bounded, and rendering charges the larger representation against its aggregate budget. Invalid compressed streams fail explicitly without changing domain/address restrictions.

## Conversation workspace

Models may choose when to read context, look up records, inspect images or use their workspace during ordinary conversation. Workspace files live at `WATCH_DATA_DIR/workspace/<scope-hash>` (`/data/state/workspace/<scope-hash>` in Docker's named runtime volume), separate from application source, Codex configuration, credentials and host mounts. Each conversation has its own files; they are not globally shared memory.

The unified file tools list/read/save/delete text and binary data using flat filenames, without directories, absolute paths, symlinks, hard links or special files. Text has a 64-KiB limit and bounded line excerpts; image/audio/video/binary bounds are described below. There is no file-count quota. Creation is the default; replacing an existing file requires `overwrite=true`. Byte streams use Store's atomic durability helper, followed by transactional index publication. Files survive context refresh and are removed when that conversation's records, group collection or departed-group data are cleared.

Workspace files are untrusted data, including any code saved as text. There is no shell, script runner, package installation or workspace-code execution capability. The MCP orchestration entry remains available only to discover/call provided tools. This workspace does not edit the bot's source or grant host access, and does not send text files as QQ attachments.

## Delivery, maintenance, and diagnostics

All application output uses `QQDelivery.send(conversationScope, content, options)`: the explicit conversation scope determines the recipient, while text, media, files and command buttons share authorization, ordering and error handling. Tool/processing hints and service errors choose administrator private scopes; ordinary model replies retain their explicitly selected conversation.

`send_reply` is available only in authorized turns. Use increasing `part_id` values and await each call. Ordinary text is one immediate message; local inline media creates ordered Markdown-text/media/Markdown-text messages, and explicit `media` follows text as a separate rich-media message. No merging, prose-length splitting, fixed ending or total reply-count cap. Empty text without media skips without QQ submission/quota; the part ID remains occupied. The entire multipart call has one idempotency ID: repeating it returns the original result, including on partial failure, without resending earlier messages. There is no special opening kind or final-text fallback. Final model JSON contains only `pauseBrowsing` and nullable `sharedState`. Silent chat turns do not trigger compensating video shares; dedicated authorized video discovery still publishes eligible saved recommendations.

QQ clients cannot load host paths. To embed a retained image between Markdown paragraphs, use `![label](asset://ASSET_ID)` or `![label](attachment://ATTACHMENT_ID)`. For retained audio use `![label](attachment://audio/ATTACHMENT_ID)`. Logical `/assets/ID` and `/attachments/ID` paths also work. These refer to actual scoped assets/attachments, never arbitrary files. The backend removes each local image expression and sends the authorized media at that position. Surrounding text stays unchanged; inline and fenced code are literal. This supports inline image syntax, not reference-style image definitions. Arbitrary local paths fail explicitly. Remote `![](https://...)` remains unchanged for QQ client rendering/loading, without a backend download or domain check; actual client display remains unverified. Explicit `media.url` downloads retain the domain allowlist. Group and routed text now use the same Markdown-capable transport as foreground replies, with conversation-local downgrade only on explicit platform rejection.

Media accepts exactly one `attachment_id`, public `url`, or image `asset_id`, with optional preceding Markdown text. Images cap at 16 MiB and audio at 8 MiB; byte formats are checked. There is no drawing/TTS service. An optional local speech decoder is available as a reusable content-flow module and operator CLI; see [audio decoder](docs/audio-decoder.md). QQ audio is available through `get_audio_detail`; local mode requires explicit runtime/model setup. Bilibili/website stream and audio integration is ON HOLD. Upload uses `srvSendMsg=false`, followed by permission/asset-existence/cancellation checks before message submission. Uncertain delivery is never replayed. Passive quotas are four private/five group messages; authorized continuations use the shared proactive queue without local timing delays.

Group More settings include an optional **reply-limit notification**, default off (`/group limit-notify-on|limit-notify-off <group-id>`), for the fifth passive model reply. That advisory is deduplicated per group for ten minutes and rechecks group opt-in before delivery. Actual QQ rate-limit rejections (HTTP 429 or business code 22009) are reported separately to bot administrators regardless of that switch, and `send_reply` receives `QQ_RATE_LIMITED` with bounded HTTP/business-code/Trace-ID metadata. They release owned reservations without pausing the group or invalidating the model turn. The rejected part is not retried or compensated through final-text/video fallback; the model may continue other work or address another authorized target. Unknown delivery and other send failures retain the stop/no-retry behavior. The shared send queue serializes operations without fixed timing delays. Notification failure is recorded without recursive reporting, source-chat fallback or retries.

Foreground private chats and authorized group discussion batches can select recipients from this turn's aliases: other allowed, push-enabled, unpaused groups, registered bot administrators and up to 100 known private contacts when public private chat is enabled. The source appears only as `current`; idle starters remain current-group-only. Models choose whether to send and which targets suit the received signal/topic/persona. Sending to another chat does not read or merge its model context or start another model turn. Private discovery/ordinary background browsing have no sending tool. Video pushes use at most one plain-text share per ten minutes per group, with permanent BV deduplication and persisted send reservations.

Other rejection or uncertain group delivery stops the affected group's tasks, invalidates queues, and saves diagnostics without retry. Administrator Start/feature enablement resumes work under existing permissions; new foreground messages can still be handled. Stopping cannot recall accepted/in-flight messages. Context refresh disconnects the model thread while retaining records; clearing needs a ten-minute single-use confirmation bound to administrator/target. Preserve model, reasoning, persona, video facts, permissions, and switches. Do not promise deletion of QQ client messages, Codex archives, or backups.

Management pages send Markdown followed by separate navigation-button messages, each with a short body. Model pages have at most five buttons, including navigation, in one column. Ordinary replies contain bodies/media without automatic menus. Group Markdown rejection downgrades only that conversation.

Cross-chat multicast uses sequential `send_reply` calls, one per target with increasing part IDs. No arbitrary-address or `all` target is accepted. Other failure/uncertainty stops remaining sends without rolling back successful targets or retrying. Explicit QQ throttling rejects only that part without stopping the turn or group. Cross-target success preserves an unsent current-chat answer. Routed replies use the shared ordered queue without local pacing delays or cross-conversation cooldowns.

`reply-contacts.json` keeps up to 100 private recipient identities/names/last-seen/stopped metadata, never chat bodies, learned from authorized non-command private events. Existing ordinary private chats enter the directory on their next valid chat message. Public-private-chat closure, recipient removal, stop and epochs are rechecked during sending. Stop tasks lists known private contacts; new authorized private messages unblock them. Scoped private clearing removes its entry, and offline all-chat cleanup removes the directory. Contact labels are untrusted routing metadata, not a directory to publish in other chats. Deployment does not enable settings or resume stopped tasks.

The administrator **Run feedback** page (`/settings display`) contains the private tool-monitoring switch and the sole diagnostic-report button. Private monitoring defaults off and covers that administrator's foreground private tasks; each group's More page separately enables processing hints and tool monitoring for authorized discussion batches. Both hint types and service errors use the same administrator-notification route, defaulting to bot administrators' private chats. They show actual allowlisted stage/tool status and elapsed time without arguments, result bodies, reasoning or model commentary. Repeated tool events remain distinct. Live source switches, cancellation and administrator membership are rechecked before sending. Hints do not consume the source chat's passive quota or count as substantive replies; failed administrator delivery is recorded without source-chat fallback, retries or stopping normal answers.

`/debug` is the sole diagnostic export entry. It returns one metadata-only UTF-8 TXT report covering the service, requesting administrator private chat and up to 50 groups, with at most 160 deduplicated events and a return-to-feedback button. It uses cached diagnostics/settings, without platform lookups, inference, message-body reads or another private conversation. Diagnostic categories and platform pages are removed. Diagnostic file delivery separately records upload/uploaded/send/sent stages, and failures identify the upload or send phase while preserving HTTP/business codes and Trace IDs. A failed TXT report does not direct the operator to send the same report again; there is no text fallback or automatic retry. Normal service notifications are brief; actual rate-limit notices include platform error metadata. Other notices omit raw codes/request IDs; structured codes, model RPC categories, platform failures and Trace IDs stay in the report. Logs/diagnostics retain stages, counts, codes, and Trace IDs; exclude prompts, bodies, member IDs, queries/URLs, credentials, and internal reasoning. Technical failures notify current bot administrators privately, with no fallback to the source group and no recursive reporting.

The `/debug` TXT report starts with recent failures and fixed recovery guidance, local-audio model-path configuration presence, current group stops, and recent requests correlated by scope/task ID. It distinguishes QQ send acceptance from tool success and old errors from current switches. Raw state, lifetime counters and ISO events remain in an appendix. It does not run model, network, dependency or model-file probes.

## Runtime and deployment

Requires Node.js 24, pinned npm dependencies, Codex CLI, and matching Playwright Chromium. Local setup:

```bash
npm ci
npm run setup:browser
cp .env.example .env
CODEX_HOME="$PWD/.auth/codex" codex login
node scripts/login.mjs
# Confirm the Bilibili QR in the app, then check the saved account:
node scripts/login.mjs --check
npm start
```

Set `QQBOT_APP_ID`/`QQBOT_APP_SECRET`; see [.env.example](.env.example) for configuration. `QQBOT_TRANSPORT` supports WebSocket or an HTTPS webhook at `/qq/callback`. `WATCH_GROUP_OPENIDS` optionally initializes the group allowlist. Never publish `.env`, `.auth`, runtime records, or QR images.

The user handles deployment using Compose; commands/paths are in [HANDOFF.md](HANDOFF.md). Use the administrator login flow or the documented local login command for Bilibili authentication. Routine rebuilds preserve the named runtime volume. Never delete that volume. Debian 13 runs non-root with a read-only filesystem and reuses host Codex/Playwright packages read-only; coordinate host-path upgrades/cleanup first.

`CodexAdapter` reuses a process/thread per live conversation scope with a default cache of two processes, subject to the group history-window expiry described above. It evicts an idle unpinned session when needed; later access starts a process and resumes its saved thread. Busy capacity returns `SESSION_LIMIT_REACHED`. Instruction/tool changes, cancellation, reset, and recovery can also replace processes. Ordinary messages do not inherently launch a process, but each response still needs inference.

Codex uses read-only sandbox/`approvalPolicy=never`, native `web_search="live"`, and the explicit per-tool MCP allowlist. Keep `code_mode_host=true` for tool discovery/orchestration; shell, file edits, built-in browser, plugins, and privilege escalation remain disabled. `CODEX_HOME` is isolated; child processes do not inherit QQ secrets or development-session MCP configuration. Search only necessary public terms and cite actual source links.

Private continuous browsing waits 30 seconds between normal rounds; transient errors back off from 60 seconds to ten minutes, while authentication/quota/configuration errors pause work. `/pause`, stop requests, and disabling the switch persistently stop browsing. Ordinary chat does not enable it.

Bilibili QR login is a separate administrator-only service: one session at a time, three-minute expiry, three-second polling, and hourly automatic reminders. QR keys/images/cookies never enter model context or chat history. Credentials are replaced only after account verification. API/network errors alone do not prove logout; video faults do not require Codex reauthentication.

Store JSON writes use exclusive temporary files, data flush, atomic rename, and directory fsync. Corrupt ordinary state raises `STATE_JSON_CORRUPT`. Only scoped/public video JSON records have locked parse-failure reread/delete recovery; missing files differ from I/O failures. Group databases retain records on diagnostic errors rather than destructive recovery.

## Offline removal of all local chat records

Stop the bot before running `node scripts/clear-chat-records.mjs --all --offline`. Use `--data-dir` and `--codex-home` for explicit service-only locations, or the configured `WATCH_DATA_DIR`/`WATCH_CODEX_HOME` values. Docker commands are in [HANDOFF.md](HANDOFF.md).

The operator command removes all scoped messages/summaries/member caches, attachment indexes, retained images, workspaces, recent activity, diagnostics, and the isolated Codex session/archive/history/memory databases. Conversation checkpoints retain only model and reasoning choices with no thread or seen-message IDs. Credentials, authorization, preferences, persona, shared role state and video facts remain. The runtime volume itself is never deleted. This is local deletion, not deletion of QQ client messages, external providers' records or backups. Subsequent authorized traffic can create new records.

## Administrator file and media management

In private administrator chat, Data management offers Files and notes (`/files`) and Attachments and images (`/media`). Each page can select the current administrator's private conversation or an authorized group's workspace/media from that group's More settings; notes also offer shared `/memory`. Other users' private workspaces are not exposed. Read-only pages bypass inference and leave task switches and checkpoints unchanged.

Text files have paginated inline bodies and complete UTF-8 TXT export through the existing private QQ upload/message path. Exports contain the original complete text, independently of the bounded model-tool excerpts. Deletion requires a short-lived administrator/scope/file confirmation; a changed file must be reviewed again. The shared `AGENTS.md` guide cannot be modified or deleted. Upload and message submission recheck administrator identity, source authorization and source existence.

Media pages distinguish received attachment indexes from saved image bytes. They list metadata without publishing tokenized QQ URLs and can explicitly deliver a selected image, voice or MP4 video to the requesting administrator's private chat. Opening retains per-item bounds: image 16 MiB, voice 8 MiB, video 64 MiB; generic received files support inline UTF-8 text paging and complete TXT export up to 64 KiB. Removing a received attachment deletes its download pointer and associated image lookup, leaving message text and separately saved copies intact. Removing a saved image deletes that retained asset. Neither action recalls QQ messages. Expired links remain explicit failures; opening does not automatically retain media.

Received attachment metadata has no documented fixed download-URL lifetime in the [official event schema](https://bot.q.qq.com/wiki/develop/api-v2/autogen/event/c2c_message_create.html). The local seven-day index retention is not a platform URL guarantee. [Upload responses](https://bot.q.qq.com/wiki/develop/api-v2/autogen/api/v2_users_user_openid_files.post.html) separately document `file_info` TTL and the returned `raw_url` lifetime; those refer to uploaded media, not arbitrary received URLs.

Selected media files can be saved in the conversation workspace. `format=auto` (default) encodes MP4 output at a bounded bitrate; received QQ MP4 stays unchanged unless `bitrate_kbps` is specified. `format=original` always preserves bytes. `format=video` emits MP4 (default at most 1,200 kbps video and 96 kbps audio, scaled within 1280×720 without upscaling; a known lower source video bitrate is preserved as the target), `format=audio` extracts/re-encodes MP3 (128 kbps default), and `format=gif` converts the entire source, with adjustable fps/width/palette and a 15-second limit. Longer/unknown GIF duration is refused, never cropped or silently changed to another format. Encoding runs only when selected, with a 90-second deadline and source-duration/dimension limits. Output limits: text 64 KiB, image/GIF 16 MiB, audio 8 MiB, video/binary 64 MiB; downloads 64 MiB. Encoding uses bounded temporary input and streams output through validation and atomic publication; failed output preserves an existing file. No multi-gigabyte ingestion or arbitrary document parser is provided. Live encoding and QQ display require operator validation.

Private administrator Data → Chat records and Group → More → Chat records now offer retained incoming-message lists (eight per page), paged body viewing and a single-record TXT export to the administrator private chat. The current private page covers only that administrator's conversation; group browsing requires current group authorization and enabled collection. These are the robot's bounded retained records, not full QQ history, and do not include a complete bot-reply transcript. Attachments remain text indexes and quoted/forwarded interiors are not expanded in this view; use Attachments and images for retained media. Existing context refresh/compaction and confirmed scoped clearing remain available. Export rechecks access and record existence before and after upload.

Workspace image/audio files can be sent with `send_reply(media={type:"image"|"audio",file_name:"saved.ext"})`; only a flat scoped name is accepted. File bytes and source existence/access are rechecked around upload. In the administrator Files and notes pages, selected media shows metadata, confirmed deletion and explicit private image/audio/video opening; text keeps paging and full TXT export.
